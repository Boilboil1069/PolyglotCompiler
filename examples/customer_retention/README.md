# Customer Retention Dashboard (HTML Frontend)

This is a real cross-language frontend example that opens directly in a browser. It uses no npm, bundler, CDN, or external language compiler. Run the local PolyglotCompiler once, then open [`index.html`](index.html).

```text
Python telemetry
      -> Java activity signal
      -> JavaScript retention score
      -> Poly validation and segmentation
      -> data/generated_accounts.js
      -> HTML / CSS / browser JavaScript dashboard
```

PolyglotCompiler's built-in lexers, parsers, semantic analyzers, and IR lowerers compile the Python, Java, and retention-policy JavaScript into one native executable. The browser UI is a zero-build static layer: `app.js` is analyzed with PolyglotCompiler's JavaScript frontend via `--check`, then executed by the browser for DOM interaction. HTML and CSS are static assets, not compiler inputs.

## Run the frontend

Build `polyc` and `polyld` at the repository root, then:

```bash
cd examples/customer_retention
./run.sh
```

Expected output:

```text
customer_retention: rows=5 healthy=1 watch=1 risk=3 checksum=45
customer_retention: frontend=index.html data=data/generated_accounts.js
```

Open `examples/customer_retention/index.html` directly in a browser. The page uses classic deferred scripts and no `fetch()` or ES modules, so it works over `file://` without a local HTTP server.

The dashboard provides KPI cards, a segment donut, score bars, searchable/filterable/sortable accounts, a cross-language trace drawer, and an in-browser audit of all five scores plus checksum `45`.

## Verify everything

```bash
./test.sh
```

The test builds with `PATH=/nonexistent`, checks the native objects/descriptors/symbols, compares both data snapshots exactly, runs PolyglotCompiler JavaScript frontend checks over all browser scripts, validates script order, and rejects modules, network requests, and external URLs.

## Business rules

- Python deterministically generates sessions, purchases, complaints, and days since login.
- Java computes `sessions * 2 + purchases * 5 - complaints * 4`.
- JavaScript subtracts `daysSinceLogin * 2` to produce retention health.
- Poly classifies scores as healthy (`>= 30`), watch (`>= 10`), or risk.

The five accounts produce one healthy, one watch, and three risk records, with checksum `45`. `data/generated_accounts.csv` is the readable reference snapshot; the compiled native program regenerates `data/generated_accounts.js`, which is what the page loads.

## Files

| File | Responsibility |
| --- | --- |
| `index.html` | Directly openable semantic HTML page |
| `styles.css` | Responsive dashboard, charts, and drawer styling |
| `app.js` | Rendering, search, filters, sorting, details, and browser audit |
| `customer_retention.poly` | Cross-language orchestration, assertions, segmentation, and data output |
| `python/telemetry_data.py` | Deterministic telemetry generation |
| `java/SignalRules.java` | Static Java activity rule |
| `javascript/retention_policy.js` | Retention policy shared by native compilation and the browser |
| `data/generated_accounts.csv` | Auditable reference snapshot |
| `data/generated_accounts.js` | Browser data generated by the native executable |
| `run.sh` | Isolated build, execution, and page-data generation |
| `test.sh` | Native-pipeline, browser-asset, and frontend-analysis audit |

## Current boundaries

The first version uses signed 64-bit integers, with browser values kept inside JavaScript's safe integer range. The native file runtime currently targets x86_64 macOS/Linux. Java local imports require the module filename to match the class that owns the static method (`SignalRules` here). Runtime CSV input, larger cohorts, trends, and real retention actions can be added incrementally.
